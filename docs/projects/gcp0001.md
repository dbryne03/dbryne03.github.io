# Google Cloud Platform #0001

## Overview

A monthly music intelligence pipeline built on Google Cloud Platform. Ingests chart, artist, and track data from three external sources, transforms it into a dimensional model in BigQuery via dbt, and surfaces insights through a four-page Data Studio dashboard.

The pipeline tracks artist chart performance, audio characteristics, and cross-source artist identity on a monthly cadence — orchestrated by a single Airflow DAG on Astronomer Cloud with full end-to-end observability.

## Objectives

1. Identify which artists are dominating the Last.fm charts and how their listener counts move month-on-month
2. Profile the audio characteristics of charting tracks using Spotify feature data
3. Contextualise artist performance with MusicBrainz metadata — country, artist type, and active years
4. Surface findings through an interactive Data Studio dashboard connected directly to BigQuery

## Sources

| Source | Name | Type | Format |
|:---|:---|:---|:---|
| A | Last.fm `chart.getTopArtists` | REST API (paginated) | JSON — chart positions, listener counts, play counts |
| B | MusicBrainz Artist Dump | Batch download | NDJSON — canonical artist metadata, genres, life-span |
| C | Spotify Tracks Dataset | HuggingFace Parquet | Parquet — audio features per track |

## Dimensional Model

| Model | Grain | Description |
|:---|:---|:---|
| `dim_artist` | One row per artist | MBID as natural key, MusicBrainz metadata (country, type, active years), `is_mb_verified` flag |
| `dim_track` | One row per `track_id` | Full Spotify audio feature set — danceability, energy, valence, tempo, key, mode, and more |
| `fact_chart_position` | One row per artist × chart week | Chart rank, listener count, play count — links to `dim_artist` |

## Data Studio Dashboard

Four pages connected directly to the `music` BigQuery dataset:

| Page | Content |
|:---|:---|
| Chart Overview | Leaderboard table of top artists by listener count for the selected chart week |
| Artist Profile | Chart history line chart and MusicBrainz metadata for a selected artist |
| Audio Features | Average danceability, energy, valence, and tempo by genre |
| Trends | Rank movement and listener growth across chart weeks for selected artists |

## Resilience Design

**Stream-publish per page.** The Last.fm producer publishes each paginated API response to Kafka immediately before fetching the next page. A retry on page N only replays from page N — pages 1..N-1 are already committed to the topic.

**Dead-letter routing.** The Kafka consumer routes malformed messages to `raw/api/lastfm/dead-letter/` rather than skipping them silently. Malformed messages can be inspected and replayed without re-running the producer.

**Data quality gates.** Each extractor validates output volume before staging to GCS — the musicbrainz extractor requires ≥1M records, the Spotify extractor requires ≥100k rows. A partial extraction fails loudly rather than landing silently incomplete data.

**Source freshness check.** `dbt source freshness` runs before `dbt run` in every pipeline execution. If any raw table has not been updated within the threshold, the transformation step is blocked and an alert is sent.

**Staging deduplication.** `stg_lastfm_charts` deduplicates on `(artist_name, chart_week)` using a `qualify row_number()` window, taking the most recently ingested record. This makes the staging model resilient to repeated pipeline runs without requiring a manual table truncation.

**Failure alerting.** All DAGs invoke `on_failure_callback` after retries are exhausted. Failures emit structured log entries to Cloud Logging and send an HTML email alert to a configured address via Airflow's SMTP backend. Three failure classes are distinguished: stale source data, dbt test failures, and infrastructure errors.

## Cross-source Artist Resolution

Last.fm, MusicBrainz, and Spotify each use different identifiers for the same artist. The intermediate layer resolves artist identity in two passes:

1. **MBID join** — primary path; precise when the chart record carries a MusicBrainz ID
2. **Normalised name fallback** — for the ~30% of charting artists without an MBID, a second join on `lower(regexp_replace(trim(name), r'[^a-z0-9 ]', ''))` matches against MusicBrainz by cleaned name

`is_mb_verified` distinguishes which path resolved each artist in the output.

## Infrastructure

All GCP resources are provisioned by idempotent shell scripts in `infra/provision/`, run automatically via GitHub Actions on every merge to `main`. Scripts source shared configuration from `infra/config.env` and check for resource existence before creating.

Authentication uses Workload Identity Federation (OIDC) — no long-lived JSON keys in GitHub Secrets.

| Resource | Details |
|:---|:---|
| GCS bucket | `portfolio-hub-2026-music-raw` — uniform bucket-level access, 90-day lifecycle on `raw/` |
| BigQuery | `raw` and `music` datasets; raw tables created from schema definitions in `dags/schemas/` |
| Artifact Registry | Docker repository `music-pipeline` (`europe-west2`) |
| Cloud Run Jobs | Five jobs — four extractors + dbt-runner; per-job CPU and memory configuration |
| Secret Manager | `lastfm-api-key`, `kafka-bootstrap-servers`, `kafka-api-key`, `kafka-api-secret` |
